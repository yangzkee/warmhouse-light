## 1. 光电巡线的物理原理

赛道上贴有 **深色线**（常见黑色电工胶带或印刷），地面为 **浅色**（白或灰）。

**红外反射式**光电管（或集成模块）向地面发射红外光，接收反射强度：

| 地面情况 | 反射 | 接收端大致表现 |
|----------|------|----------------|
| **白底** | 强 | 输出高电平 / 判为「亮」 |
| **黑线** | 弱（吸收多） | 输出低电平 / 判为「暗」 |

**注意**：环境光、高度、地面材质、发射电流都会改变阈值，所以模块上常有 **电位器调阈值**，或固件里做 **自适应/数字模式** 切换。

本工程把每路传感器最终变成 **数字量**：`0 = 黑线`，`1 = 白底`（与 `ir_grayscale.h` 注释一致）。

### 图 1-1：反射式光电（概念）

```text
  ┌──────── 车上模块 ────────┐
  │  [发射 IR]    [接收]    │
  └──────┬───────────▲───────┘
         │ 照射      │ 反射强度
         ▼           │
      ═══════ 地面 ═══════
         │
         └──► [模块内比较阈值] ──► [单路数字量: 0=黑, 1=白]
```

## 2. 从电压到数字量：本工程的传感器接口

- 硬件：**亚博 8 路灰度**（或类似协议），经 **USART2** 以 **ASCII 文本包** 发回（如 `$D,x1:0,x2:0,...#`）。
- 固件：`ir_grayscale.c` 逐字节解析，`IR_Data_number[0..7]` 存 8 路 0/1。
- 上电后 `main.c` 中调用 **`IR_Send_Control_Data(0,0,1)`** 切换到 **数字输出模式**，便于稳定二值化。

因此：**不是 MCU 直接读 ADC**，而是**传感器模块内部已判黑白**，MCU 只解析串口。

### 图 2-1：灰度数据进入 MCU 的路径

```text
  [8 路灰度模块]
        │  UART 文本包
        ▼
  [USART2 RX 中断]
        │
        ▼
  [Deal_IR_Usart 组帧]
        │
        ▼
  [Deal_IR_Usart_Data 解析]
        │
        ▼
  [IR_Data_number[0..7]]
```

## 3. 8 路探头与 pattern：车相对黑线在哪一侧

探头排列为 **横向一条线**（车前进方向垂直于探头排列），从左到右记为 **L1…L8**（代码里 `IR_Data_number[0]` 最左，`[7]` 最右）。

定义 **8 bit pattern**（与 `nav_sense.h` 一致）：

```text
pattern = (L1<<7) | (L2<<6) | … | (L8<<0)
```

其中某位为 **0** 表示该探头**在黑线上**（见黑），为 **1** 表示**白底**。

- **线在车左侧**：往往左侧几个探头见黑，右侧见白 → 用加权/查表得到 **偏差 err**（本工程约定：**线在左侧 err>0**，要左转把线拉回中间）。
- **线在车右侧**：err<0。
- **直行居中**：中间探头压黑，err≈0。

`LineTracking.c` 里在 **直道** 会强化 **L4/L5** 压黑、在 **直角弯** 对特定 pattern 抬高 **|err| 下限**，让 PID 更果断转向；这些属于 **几何与查表融合**，见 `LineTracking.c` 头部注释。

### 图 3-1：从 8 路到偏差 err（抽象）

```text
  IR_Data_number[0..7]  ──►  合成 pattern (8bit)
                                    │
                                    ▼
                          查表 / 加权 / 直道几何校正
                                    │
                                    ▼
                          偏差 err（左正右负）
```

## 4. PID 循迹：偏差 err 与控制量 sendVel

**PID**（比例–积分–微分）用 **err** 作为输入，输出一个 **角速度修正**（本工程通过 **`sendVel(Vx, Vy, Vz)`** 发给底盘）。

- **P**：与当前 err 成正比，快速响应。
- **I**：消除稳态偏差（注意积分饱和）。
- **D**：抑制振荡、对 err 变化敏感。

**主循环**（`LINE_TRACK_LOOP_MS`，一般为 4ms）调用 **`LineTracking_Step()`**，但 **PID 与 sendVel 的更新**与 **光电新包** 同步（`had_new` 时才算新 err），积分 dt 用**相邻两包时间间隔**，避免串口抖动导致积分错误。

**底盘约定**（见 `LineTracking.c` 头部）：

- `V_y>0`：前进；
- `V_z`：绕竖轴旋转分量（与左转/右转符号约定一致，代码里用 `vz = -PID_Calc(err)` 等形式与约定对齐）。

**局限**：PID 只解决「**跟着线**」；**路口**（多条黑线、全白丢线、直角、T 字）需要 **状态机** 或 **里程/导航** 辅助，见后文。

### 图 4-1：单周期内「光电 → PID → 底盘」的逻辑（简化）

```text
            ┌─────────────────────────┐
            │  LineTracking_Step()    │
            └───────────┬─────────────┘
                        │
                        ▼
              ┌─────────────────┐
              │ 本周期有新光电包？ │
              └────────┬────────┘
                  否   │   是
           ┌───────────┴───────────┐
           ▼                       ▼
   [保持上一帧 vy/vz]      [算 err → PID，dt=包间隔]
   [避免指令断档]                   │
           │                       ▼
           │                [sendVel 下发]
           │                       │
           └───────────┬───────────┘
                       ▼
                 (下一周期再进入)
```

## 5. 仅靠光电的局限：为什么需要里程与 ODOM

- **光电**只能看到**局部**一条线；在 **十字路口、T 字、多条分支** 时，同一 pattern 可能对应多种路径。
- **全白**（`pattern==0xFF`）表示 **丢线**（出界或间隙），需要 **记忆策略**（减速、原地找线、按预设转弯）或 **ODOM** 推一段距离。
- **比赛地图**常要求：在某一里程 **必须左转/右转/停车**，或 **迷宫段** 与 **普通循迹段** 行为不同。

本工程使用 **Dcar 底盘经 USART1 回传的 ODOM**（`DF_Communication` 解析到 `g_odom`），由 **`nav_odom.c`** 做：

- 累计路程、积分 `x/y`（在底盘坐标系下）；
- 航向 `yaw`、相邻帧 **Δyaw**（判断转弯方向）；
- 与电机/减速器相关的 **标定**（`NavOdom_SetProfile` 步进/光编等）。

**重要**：`nav_odom.h` 说明 —— ODOM 给出的是**底盘坐标**下的位置，**不是**赛道绝对坐标；除非你在起点对零并与地图对齐，否则「米」是**相对路程**含义，用于与 **nav_route 里程表** 对齐。

### 图 5-1：光电 + 底盘 ODOM 如何同时进巡线

```text
  USART1:  Deal_DF_Usart ──► g_odom ──► NavOdom_UpdateStep（路程/x/y/Δyaw）
                                              │
  USART2:  IR_Data_number ────────────────────┼──► LineTracking
                                              │
  里程:    nav_route（用累计路程判定）────────┘
                                              │
                                              ▼
                                        sendVel ──► 底盘
```

## 6. 本工程的「地图适配」分三层

可以把它理解成从「**贴线**」到「**按地图跑**」的三层：

| 层次 | 模块（主要） | 作用 |
|------|--------------|------|
| ① 循迹层 | `LineTracking.c` + `ir_grayscale` + `nav_sense` | 跟黑线、算 err、PID、路口/迷宫子状态机 |
| ② 里程策略层 | `nav_route.c` | **按累计路程（米）** 触发 **左转/右转/直行/停车** 等离散动作，与 `NavOdom_GetTotalDistanceM` 对齐 |
| ③ 拓扑层（可选） | `nav_path.c` | **边表 + 从终点反向 BFS**，适合「已知固定地图」的 **多路口** 决策；RAM 有限时也可用静态表 |

### 图 6-1：三层关系（数据流）

```text
  ① 循迹层:   光电 pattern ──► err + PID + 路口/迷宫状态机 ──┐
                                                           │
  ② 里程层:   累计路程 ──► nav_route 按米触发 ────────────┼──► sendVel
                                                           │
  ③ 拓扑层:   nav_path 边表 ──► BFS 得下一跳动作 ─────────(可选汇入循迹)
```

## 7. 里程节点表 nav_route：按米触发动作

`nav_route.h` 定义了 `NavRouteNodeDef_t`：

- **`trigger_dist_m`**：从某一起点累计走过的路程（米）达到该值时触发；
- **`act`**：`LEFT` / `RIGHT` / `STRAIGHT` / `IGNORE` / **`STOP`**（巡线结束、速度置零等）；
- **`guide_ms`**：触发后给 PID 一段「引导时间」（与 `ROUTE_GUIDE_ERR` 等配合，把 err 拉向目标方向）。

`NavRoute_TryFire(total_dist_m, lead_m, ...)` 根据 **当前里程** 判断是否命中下一节点；`lead_m` 为 **提前量**（例如提前 8cm 开始转向引导）。

**如何适配「地图」**：把赛道拆成 **若干段**，在 **关键距离** 上配置 **动作**（例如「第 3 米必须右转进迷宫」）。**地图变化**（长度不同）主要改 **这张表** 或 **标定系数**（`NavRoute_PhysicalMToOdomTotalM` 等与 ODOM 单位一致）。

### 图 7-1：按里程触发下一节点（抽象）

```text
  NavOdom_GetTotalDistanceM()
            │
            ▼
  NavRoute_TryFire(total, lead_m)
            │
            ▼
     ┌──────┴──────┐
     │ 到下一节点   │
     │ 触发距离？   │
     └──────┬──────┘
        否  │  是
    ┌───────┴───────┐
    ▼               ▼
 [继续纯循迹 PID]  [输出 act: 左/右/直/停…]
                           │
                           ▼
              guide_ms 内用 ROUTE_GUIDE_ERR 拉偏 err
```

## 8. 拓扑层 nav_path：固定赛道上的「图论」骨架

`nav_path.h` 描述 **边表**（`from`→`to`，`length_m`，`act_at_to`）与 **节点**（可带 `x`、`y`）。

**典型用法**（注释中两阶段）：

1. **探索/建图**：在路口用 ODOM 近似位置建节点/边，或 **手动** 填表；
2. **行驶**：`NavPath_BfsFromGoal(goal_id)` 后，在路口用 **`NavPath_PickActionFromEdge`** 等选下一条边。

**与 nav_route 的关系**：`nav_route` 更像 **一维里程表**；`nav_path` 是 **二维拓扑 + 最短路**，适合**多分支、多圈**的赛道。本工程若**赛道固定**，可**纯静态表**（注释所述）。

### 图 8-1：拓扑 + 反向 BFS（概念）

```text
  NavPath_AddEdge（录入节点与边表）
            │
            ▼
  NavPath_BfsFromGoal(终点)
            │
            ▼
  每个节点记下「朝终点走」的下一跳边
            │
            ▼
  到路口：根据当前节点查表选动作
```

## 9. 双图镜像 LineTrack_MapDetect：同一套表跑两种场地布局

`LineTracking.h` 中：

- **`LineTrack_GetMapMirror()`**：返回 **+1** 或 **-1**，表示 **「图1」**（ODOM `x` 相对基准增大）或 **「图2」**（`x` 减小）。

`LineTracking.c` 中 **`LineTrack_MapDetect_Tick`**（受 `LT_MAP_DETECT_ENABLE` 控制）逻辑要点：

1. 起步先走够 **`LT_MAP_DETECT_ARM_DIST_M`**（默认约 0.6m）再记一次 **`x_ref`**，避免起步抖动误判。
2. 若 **`|pos_x - x_ref|`** 超过 **`LT_MAP_DETECT_DX_TH`**（默认约 0.1m），则锁存 **镜像**（`s_map_mirror = ±1`）并 **锁定**。
3. 若累计路程超过 **`LT_MAP_DETECT_FALLBACK_DIST_M`**（默认约 4m）仍达不到阈值，则 **默认图1**。

**意义**：同一套 **nav_route 与行为**，在 **左右对称** 或 **两种发车方向** 的场地上，用 **ODOM 的 x 漂移方向** 区分「当前是哪张图」，从而 **镜像** 迷宫横移符号、8 字方向等（见 `s_map_mirror` 注释）。

### 图 9-1：双图检测 LineTrack_MapDetect_Tick（与代码分支对应）

```text
  [未锁定 且 LT_MAP_DETECT 开启]
            │
            ▼
      g_odom 有效？──否──► 返回等待
            │是
            ▼
  累计路程 ≥ FALLBACK？──是──► 默认图1，锁定结束
            │否
            ▼
  路程 ≥ ARM 且尚未记 x_ref？──是──► x_ref = 当前 pos_x
            │否
            ▼
      计算 dx = pos_x - x_ref
            │
            ▼
      |dx| > DX_TH ？
       /    |     \
   否 /     |      \ 是
     /      |       \
    返回    dx 大正   dx 大负
   等待    图1锁定   图2锁定
          mirror=+1  mirror=-1
```

## 10. 路口与迷宫：光电状态机 + 里程约束

- **`nav_sense`**：用 `pattern` 统计 **见黑数量**、**疑似路口**、**全白丢线** 等提示，**不替代** `LineTracking` 的 PID。
- **`LineTracking.c`** 内含 **拐角/迷宫** 等 **状态机**（注释中：横竖线、直角、T 字、盲走横移等），并在 **迷宫段** 用 **`NavOdom_MarkSegmentStart` / `GetDeltaSinceLastMarkM`** 等做 **段长对称**（例如右横移距离与左横移对称）。
- **`LT_MAZE_YAW_CHK_*`**（可选）：在一段窗口内用 **累计 Δyaw** 与 **nav_route 期望动作**（左/右/直）做 **一致性校验**，用于调试串口打印 `MAZE,...`，**不替代** 主控制逻辑。

### 图 10-1：感知与决策（简化，非完整状态机）

```text
        pattern ──────┬────────► LineTracking（PID + 路口/迷宫子状态机）
                      │
  nav_sense（BlackCount / JunctionHint）──┘
                      │
  ODOM / 段长 Mark ───┘
                      │
                      ▼
                  sendVel
```

> **说明**：真实 `LineTracking.c` 内迷宫、直角、T 字等 **状态非常多**，此处只画 **数据从哪来、往哪汇聚**；调参时请结合源码中的枚举与注释。

## 11. 如何把「地图/规则」写进代码

**实操顺序建议**：

1. **纯循迹**：`USE_LINE_TRACKING=1`，先保证 **USART1/2** 波特率与接线正确，PID 能稳定跑直线与缓弯。
2. **标定 ODOM**：`NavOdom_SetProfile` 与 `NAV_ODOM_*` 比例与实车一致，使 **`NavOdom_GetTotalDistanceM()`** 与卷尺/跑道标记接近。
3. **填里程表**：在 `nav_route` 的表（或 `nav_route.c` 中数据）里按 **米** 设置 `trigger_dist_m` 与 `act`，用 `NavRoute_TryFire` 驱动 `LineTracking` 的 **引导/停车**。
4. **复杂拓扑**：若有多条可选分支，用 **`nav_path`** 建边表 + BFS，或比赛时直接 **硬编码** 每段路口动作。
5. **双图/镜像**：若官方有两套对称地图，打开 **`LT_MAP_DETECT_*`** 相关宏，调 `ARM/DX/FALLBACK` 距离，观察 **`LineTrack_GetMapMirror()`** 与实车 ODOM。

## 12. 附录：术语对照

| 术语 | 含义 |
|------|------|
| 光电管 / 灰度 | 本工程指 **8 路红外反射** 数字输出 |
| pattern | 8bit 黑白图案编码，**0=黑** |
| err | 相对赛道中线偏差，**左正右负**（本工程约定） |
| ODOM | 底盘里程计协议（`g_odom`），含位姿与航向 |
| nav_route | **一维里程节点表** |
| nav_path | **拓扑图 + BFS** 骨架 |
| 地图（本工程） | 多指 **赛道几何 + 规则**，通过 **表 + 状态机 + ODOM** 实现，而非 SLAM 栅格地图 |
